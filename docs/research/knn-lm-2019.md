# Generalization through Memorization: Nearest Neighbor Language Models (Khandelwal, Levy, Jurafsky, Zettlemoyer, Lewis; 2019)
**Source:** https://arxiv.org/abs/1911.00172  **License:** arXiv's standard perpetual, non-exclusive distribution license (arXiv id `nonexclusive-distrib/1.0`) — not CC-BY; treat as link-and-attribute only, not freely reproducible.

## What it does (plain words)
This paper asks: what if a language model didn't have to memorize every fact and phrase in its own weights, and could instead look things up? The authors take a normal, already-trained Transformer language model and bolt on a lookup table built from the entire training set: for every point in the training text, they save "what the model was thinking right before it predicted the next word" together with what that next word actually was. At generation time, the model does its usual prediction, but also checks that lookup table for training-time moments that "felt similar" to right now, and blends in whatever words followed those moments. No retraining of the model itself is needed — just this added memory and a blending step. The result, called kNN-LM, beat the previous best word-prediction model on a standard benchmark by a solid margin, and could be redirected to a new topic domain just by swapping in a different lookup table.

## Method (the mechanism, in our own words)
The base model is a standard autoregressive Transformer LM. During (or after) training, the authors run it once over the entire training corpus and, for every token position, record a key-value pair: the key is the model's internal hidden-state vector right before it turns that vector into a word-probability distribution (i.e., the representation of "everything the model has read so far"), and the value is the actual next token that followed. Doing this for the whole corpus produces a datastore with one entry per training token — for WikiText-103 that's on the order of 100M+ entries, and in a larger-scale experiment (Wiki-3B) around 1.6B entries.

At inference, generation proceeds normally to get the base model's next-token distribution, p_LM. Simultaneously, the current hidden-state vector is used as a query into the datastore via approximate nearest-neighbor search (FAISS) under L2 (Euclidean) distance, retrieving the k=1024 closest stored keys. Those neighbors' distances are turned into a second probability distribution over next tokens, p_kNN, by converting negative distance into a softmax. The final prediction is a simple linear interpolation, λ·p_kNN + (1−λ)·p_LM, with λ tuned per setting (0.25 in-domain, 0.65 for cross-domain adaptation, where retrieval is trusted more). The clever part isn't the retrieval mechanics — it's that the "key" is the model's own learned representation of context, so nearest-neighbor search operates in a semantically meaningful space rather than on raw text or n-grams.

## Key findings
- On WikiText-103, the base Transformer LM scores dev/test perplexity of 17.96 / 18.65. Adding kNN-LM alone brings this to 16.06 / 16.12, and stacking a continuous-cache mechanism on top reaches 15.81 / 15.79 — a 2.9-point test perplexity improvement, state-of-the-art at publication, with zero additional training.
- Domain adaptation without retraining: a Transformer LM trained only on Wikipedia (Wiki-3B), evaluated on a Books-domain test set, scores dev/test perplexity 37.13 / 34.84. Simply swapping in a Books-domain datastore (same frozen model, no fine-tuning) drops this to 24.85 / 20.47 — closing most of the gap to a model actually trained on Books (14.75 / 11.89 dev/test).
- Datastore size matters a lot and hadn't saturated at the scales tested: perplexity kept improving as the datastore grew toward ~1.6B key-value pairs, with no sign of diminishing returns even at that scale. Notably, a much smaller model paired with a large datastore could outperform a bigger model trained on the full corpus outright — retrieval substituted for both training data and model capacity.
- Cost is real: scoring the WikiText-103 validation set with k=1024 retrieval per token took roughly 25 minutes using approximate nearest-neighbor search, a nontrivial overhead layered on top of ordinary LM inference.

## What Tilde should take from it
This is close to a template for the personalization path Tilde is already circling. Tilde currently has an on-device n-gram next-word model awaiting promotion into serving; kNN-LM is essentially the generalized, learned-representation version of that same idea — a nonparametric memory interpolated with the base model's distribution, with zero fine-tuning of the ~2B bundled model. Instead of (or in addition to) promoting an n-gram model, Tilde could maintain a small per-user datastore built the same way: every word the user actually types, keyed by the bundled model's hidden state at that point, with the typed word as the value. At suggestion time, interpolate the base model's next-token distribution with a lookup over that personal datastore. Unlike n-grams, this generalizes past exact phrase matches — a rare-but-semantically-similar context can still surface the user's habitual word choice, which should move EM@1 and keystrokes-saved on exactly the long-tail, idiosyncratic vocabulary (names, jargon, pet phrases) the eval quiz is meant to reward. It also updates instantly as the user writes more, with no retraining step, and stays fully local — consistent with Tilde's on-device, personalization-is-not-central-and-not-central-server design.

The λ-tuning finding is the actionable detail: the paper needed different blend weights for in-domain (0.25) versus domain-shifted (0.65) settings, and got there by direct measurement. Tilde should treat λ (or an equivalent blend/gating weight) as something to sweep against the continuation quiz rather than something to guess, and probably needs it to vary by confidence or by how much personal data exists yet — a brand-new user's tiny datastore should be trusted far less than a base-model prediction, the mirror image of the paper's domain-adaptation regime.

## Limits and caveats
The gains in this paper come from a datastore with 100M+ to ~1.6B entries; a single Tilde user's own writing is orders of magnitude smaller (more like thousands to low tens of thousands of tokens), and it's untested whether kNN-style retrieval still helps at that scale versus just being noise the base model or the existing n-gram model already covers. The reported retrieval cost (~25 minutes for one validation pass with FAISS-approximate search) is a batch, GPU-backed benchmark-run cost with no stated per-token latency comparable to Tilde's per-keystroke, sub-second budget (first-visible suggestion budget ~450ms) — this needs a fresh, on-device latency measurement before it can be trusted, not an assumption that it transfers. The evaluation itself is long-form Wikipedia/Books-style perplexity and cross-domain adaptation, not short input-method completions scored by EM@1 or keystrokes-saved, so the headline numbers aren't directly comparable to Tilde's north-star metric. Finally, the "key" is the pre-softmax hidden state of a specific architecture the authors trained; using Tilde's bundled base model's internal representation the same way would need its own validation that the representation space is well-behaved enough for nearest-neighbor lookup to be meaningful rather than just adding a slow, unhelpful mechanism suggestions must never introduce more interruption than help.
